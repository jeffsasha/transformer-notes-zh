# 33｜流水线并行：把模型切成段，为什么还有一半时间在等？

> **阅读目标**：理解流水线并行把模型按层切开后，计算为什么仍然不是满负荷的；能从"填满—稳定—排空"三段推导出气泡占比公式 $`\frac{P-1}{M+P-1}`$，并算出给定卡数和 micro-batch 数时的气泡与加速比；明白 GPipe 与 1F1B 的区别不在时间而在显存；知道流水线并行与张量并行在通信量上的根本差异。
>
> **前置知识**：第 07 篇的完整 Transformer 结构（层是顺序依赖的）；第 16 篇的梯度检查点（激活要留到反向时用）；第 31 篇的数据并行与张量并行（3D 并行的三种切分、all-reduce 的 $`2S`$）；第 15 篇的混合精度（激活显存的量级概念）。需要一点排队直觉：一段流水线里，任何工位空闲都是浪费。

## 1. 直觉：切开模型只是第一步，让每张卡一直有活干才是难题

第 31 篇讲过三种切分：数据并行切 batch，张量并行切一层内部的矩阵，流水线并行切层——把 80 层模型切成 8 段，每张卡拿 10 层。听起来很美好：模型塞进去了，8 张卡同时开工。

但"同时开工"有个前提：第 2 段要等第 1 段算出第一个 micro-batch 的激活，才能开工；第 8 段要等前面 7 段依次算完。训练刚开始时，只有第 1 段在干活，其余 7 张卡在空等——这就是流水线的**填满（fill）**阶段。结尾也一样：第 1 段算完最后一个 micro-batch 就收工了，后面 7 段还在收尾——**排空（drain）**阶段。

可以把流水线想象成汽车工厂的装配线：8 个工位依次装 8 个部件，一辆车（一个 micro-batch）必须按顺序经过所有工位。装配线刚启动时，只有第一个工位有车可装；收工时，只有最后一个工位还在忙。工位本身没有坏，车也没有少，浪费来自**顺序依赖**：下游工位的第一件活，依赖上游工位的第一件活完成。

为什么非要用流水线？因为有些模型单卡根本装不下。第 31 篇讲过，数据并行要求每张卡都存一份完整模型；当模型大到连权重加优化器状态都塞不进一张卡时（第 32 篇的 ZeRO 能分摊优化器状态，但权重本身仍需分片存放），唯一的办法就是把模型切开。张量并行切一层内部，流水线并行切层与层之间——两种切法经常一起用。换句话说，数据并行复制模型、流水线并行切分模型，前者解决"数据太多"，后者解决"模型太大"，这是两类并行最本质的分工。

填满和排空期间，总有卡在空转。这些空转的时间叫**气泡（bubble）**。本篇的核心问题就是：气泡有多大？能不能把它压小？代价是什么？

先给结论（后面推导）：$`P`$ 段流水线、$`M`$ 个 micro-batch 时，气泡占总时间的比例约为：

```math
\text{气泡占比}=\frac{P-1}{M+P-1}
```

$`M`$ 远大于 $`P`$ 时气泡可以忽略；$`M`$ 和 $`P`$ 差不多时，接近一半时间都在等。这就是标题问题的答案。

> 结论性质：这是"每段每 micro-batch 耗时相等"的理想模型下的**严格推导**；真实训练中各段耗时不均、通信有延迟，气泡只会比公式更大。公式给出的是下界，不是承诺。

## 2. 核心推导：总时间为什么是 $`(M+P-1)\cdot t`$

先把假设写在前面，本节所有结论都依赖它们：

- 模型切成 $`P`$ 段，放在 $`P`$ 张卡上；
- 一个 global batch 切成 $`M`$ 个 micro-batch，逐个流过流水线；
- 一个 micro-batch 在一段上的"前向 + 反向"总耗时为 $`t`$，且各段、各 micro-batch 的 $`t`$ 都相等；
- 忽略段间传输激活/梯度的时间（第 7 节再把它加回来）。

先看一张小时间表：$`P=4`$ 段，$`M=4`$ 个 micro-batch，格子里的数字是正在算的 micro-batch 编号，空白表示该段在空等：

| 时间步 | 段 1 | 段 2 | 段 3 | 段 4 |
|:-:|:-:|:-:|:-:|:-:|
| 1 | m1 | | | |
| 2 | m2 | m1 | | |
| 3 | m3 | m2 | m1 | |
| 4 | m4 | m3 | m2 | m1 |
| 5 | | m4 | m3 | m2 |
| 6 | | | m4 | m3 |
| 7 | | | | m4 |

一共 7 个时间步。第 1–3 步是填满，第 4 步是唯一"全满"的一步，第 5–7 步是排空。规律很清楚：最后一个 micro-batch 必须依次穿过 $`P`$ 段，而第一段又必须依次处理 $`M`$ 个 micro-batch，两件事串起来，总时间就是：

```math
T_{\text{总}}=(M+P-1)\cdot t
```

气泡占比用"利用率"来算最干净。总工作量是 $`M`$ 个 micro-batch × $`P`$ 段，每份耗时 $`t`$：

```math
\text{总工作量}=M\cdot P\cdot t
```

总容量是 $`P`$ 张卡 × 总时间 $`(M+P-1)\cdot t`$。两者相除：

```math
\text{利用率}=\frac{M\cdot P\cdot t}{P\cdot(M+P-1)\cdot t}=\frac{M}{M+P-1},\qquad \text{气泡占比}=1-\frac{M}{M+P-1}=\frac{P-1}{M+P-1}
```

这就是开头的公式。两个极端一眼就能看出来：$`M\gg P`$ 时利用率趋近 1；$`M=P`$ 时利用率约为 $`1/2`$——一半时间在等。

换个角度也能得到同一个公式：**关键路径（critical path）**。一个 micro-batch 从进入第 1 段到走出第 $`P`$ 段，最少需要 $`P\cdot t`$（必须依次穿过所有段，无法并行）；同时第 1 段处理全部 $`M`$ 个 micro-batch，最少需要 $`M\cdot t`$。这两条约束叠加：最后一个 micro-batch 要等前面 $`M-1`$ 个在第 1 段排完队（$`(M-1)\cdot t`$），再自己穿过 $`P`$ 段（$`P\cdot t`$），总计 $`(M+P-1)\cdot t`$。两种算法殊途同归，公式是稳的。

还有一个边界情况值得算：$`M<P`$ 时会怎样？比如 $`P=8`$，$`M=2`$，气泡占比 $`7/9\approx 78\%`$，8 张卡里最多同时只有 2 张在干活——切得越碎、micro-batch 越少，流水线越像单卡在干活。这就是为什么实践中 $`M`$ 至少要是 $`P`$ 的几倍。

> 关于 $`t$` 的一个细节：本节把一个 micro-batch 在一段上的"前向 + 反向"合并成一个 $`t`$。实际上反向的计算量约为前向的 2 倍（既要算对激活的梯度、又要算对权重的梯度），所以 $`t=t_f+t_b\approx 3t_f`$。只要每段、每个 micro-batch 的前向和反向耗时都各自相等，合并成一个 $`t`$ 的推导就仍然成立；不相等时，公式要按"最慢的那一段"重新算，气泡更大。第 7 节会回到这个问题。

> 注意公式里没有通信时间。真实流水线里段间还要传激活和梯度，$`t`$ 里要再加上传输时间，气泡只会更大。第 7 节会算这笔账。

## 3. 数值示例：8 卡、32 个 micro-batch 的账

取一个贴近真实训练的数：$`P=8`$ 段，$`M=32`$ 个 micro-batch，每个 micro-batch 在一段上的前向 + 反向耗时 $`t=100\,\text{ms}`$。

- 流水线总时间：$`(32+8-1)\times 100\,\text{ms}=3.9\,\text{s}`$
- 单卡顺序算完的耗时：$`32\times 8\times 100\,\text{ms}=25.6\,\text{s}`$
- 实际加速比：$`25.6/3.9\approx 6.6\times`$，理想是 $`8\times`$，气泡吃掉了约 18%
- 气泡占比：$`7/39\approx 18\%`$

换两个 $`M`$ 看趋势（$`P`$、$`t`$ 不变）：

| $`M`$ | 总时间 | 气泡占比 | 加速比（理想 8×） |
|:-:|:-:|:-:|:-:|
| 8 | $`1.5\,\text{s}`$ | $`7/15\approx 47\%`$ | $`4.3\times`$ |
| 32 | $`3.9\,\text{s}`$ | $`7/39\approx 18\%`$ | $`6.6\times`$ |
| 64 | $`7.1\,\text{s}`$ | $`7/71\approx 10\%`$ | $`7.2\times`$ |

结论很直观：**想压气泡，就要让 $`M`$ 远大于 $`P`$**。但 $`M`$ 不能无限放大：global batch 固定时，$`M`$ 越大意味着每个 micro-batch 越小，kernel 效率下降、通信占比上升；而且 micro-batch 越小，下一节说的显存问题反而越轻——这两个方向要一起权衡，净效果是**需实验验证**的调参问题，不是公式能直接给出的。

$`M`$ 也不是自由参数，它由 global batch 决定。流水线并行里，一个 optimizer step 处理的样本数是：

```math
\text{global batch}=\text{数据并行度}\times M\times\text{micro-batch 大小}
```

梯度在 $`M`$ 个 micro-batch 之间累积（第 10 篇的梯度累积概念），攒满一个 global batch 才做一次 optimizer step。所以增大 $`M`$ 有两条路：增大 global batch（第 30 篇讲过，batch 太大要配合调学习率），或者减小 micro-batch（kernel 效率下降）。实践中常把 micro-batch 设为"刚好塞满单卡显存减去激活预算"的大小，再用 global batch 反推 $`M`$。

再算一个更接近真实大模型训练的数：80 层模型切成 $`P=8`$ 段，每段 10 层；global batch 含 1024 条序列，micro-batch 为 8 条序列，数据并行度为 1，则 $`M=1024/8=128`$。每 micro-batch 每段耗时 $`t=200\,\text{ms}`$：

- 流水线总时间：$`(128+8-1)\times 200\,\text{ms}=27.0\,\text{s}`$
- 气泡占比：$`7/135\approx 5.2\%`$
- 单卡顺序耗时：$`128\times 8\times 200\,\text{ms}=204.8\,\text{s}`$，加速比约 $`7.6\times`$

气泡只有 5%，看起来很美——但别忘了这是理想模型：段间通信、段不均衡、检查点重算都还没算进去。第 7 节会把这几项加回来。

最后区分两个容易混淆的量：**延迟**与**吞吐**。流水线没有让任何一个 micro-batch 变快：单个 micro-batch 从进入第 1 段到走出第 8 段，仍然需要 $`P\cdot t`$，延迟一点没变。流水线提升的是**吞吐**：稳定期每 $`t`$ 时间就有一个 micro-batch 走完，全系统每步产出约 $`1/t`$ 个 micro-batch，而不是单卡的 $`1/(P\cdot t)`$。这和工厂装配线一模一样——每辆车的组装时间没变，但单位时间下线的车变多了。评估流水线并行时看吞吐（加速比），而不是单个样本的延迟。

## 4. GPipe 与 1F1B：把"先算完所有前向"改成"一前一后"

气泡公式只说了"时间"，没说"显存"。两种经典调度的时间账完全一样，显存账天差地别。

**GPipe**（Huang et al., 2019）：所有 micro-batch 的前向全部跑完，再统一反向。实现简单，但每段要把全部 $`M`$ 个 micro-batch 的激活都存下来，等反向时用。显存与 $`M`$ 成正比——$`M`$ 越大压气泡越有效，显存也越爆炸，正好撞上第 3 节的结论。

**1F1B**（one forward, one backward；Megatron-LM, Narayanan et al., 2021）：每段"做一个前向、做一个反向"交替进行。刚开始有一个暖机（warmup）阶段：第 $`i`$ 段（从 0 开始编号）先连续做 $`P-1-i`$ 个前向——第 0 段先做 $`P-1`$ 个前向，最后一段 1 个都不用等，做完前向立刻反向。暖机结束后进入稳定期：每段每步一个前向配一个反向，算完一个 micro-batch 的反向就释放它的激活。

同样用 $`P=4`$、$`M=4`$ 画一张表（F 表示前向，B 表示反向，数字是 micro-batch 编号；每个格子占一个单位时间）：

| 时间步 | 段 1 | 段 2 | 段 3 | 段 4 |
|:-:|:-:|:-:|:-:|:-:|
| 1 | F1 | | | |
| 2 | F2 | F1 | | |
| 3 | F3 | F2 | F1 | |
| 4 | F4 | F3 | F2 | F1 |
| 5 | | F4 | F3 | F2 |
| 6 | | | F4 | F3 |
| 7 | | | | F4 |
| 8 | | | | B1 |
| 9 | | | B1 | B2 |
| 10 | | B1 | B2 | B3 |
| 11 | B1 | B2 | B3 | B4 |
| 12 | B2 | B3 | B4 | |
| 13 | B3 | B4 | | |
| 14 | B4 | | | |

这张表有个值得留意的细节：$`M=P=4`$ 时，1F1B 实际上退化成了 GPipe 式的调度——所有前向跑完才开始反向，所谓的"一前一后"稳态根本没出现。段 1 在第 4 步做完 F4 之后，要等到第 11 步才能做 B1：因为 m1 的反向要从段 4 一路传回来，而段 4 的 F1 直到第 7 步才做完。什么时候 1F1B 才真正"交替"起来？要 $`M`$ 明显大于 $`P`$，让暖机结束时后面还有足够多的 micro-batch 可供交替——这又是"想压气泡就要 $`M\gg P`$" 的一个证据。

总时间步是 14 步。画图时为方便设前向与反向各占一个单位时间（实际反向约为前向的 2 倍，但这只改变单位换算）：按 $`t=t_f+t_b`$ 换算，总时间 $`=7\cdot t=(M+P-1)\cdot t`$，与第 2 节的公式完全一致。两种调度在理想模型下没有时间差，差别只在**同一时刻攒了多少份激活**：这张表里段 1 在第 4 步同时攒着 m1–m4 的激活（4 份），而 $`M=32`$ 时 GPipe 要攒 32 份，1F1B 仍然最多攒约 $`P=4`$ 份——第 5 节算这笔账。

关键结论，值得单独强调：**在第 2 节的理想模型下，1F1B 的总时间和气泡占比与 GPipe 完全相同，都是 $`(M+P-1)\cdot t`$ 和 $`\frac{P-1}{M+P-1}`$。** 1F1B 省的是显存，不是时间。把"1F1B 更快"当成直觉是错的——它真正的收益是：省下的显存可以换更大的 $`M`$，而更大的 $`M`$ 才能压低气泡。时间上的收益是间接的。反过来也可以说：GPipe 的问题从来不是"慢"，而是"显存撑不住足够大的 $`M`$"——调度之争的本质是显存之争。

## 5. 显存账：为什么 1F1B 能把激活从 $`M`$ 份压到 $`P`$ 份

设每个 micro-batch 在一段上产生的激活占 $`A`$ 字节（前向结果要留到反向用，第 16 篇的检查点讨论过同一笔账）。

- **GPipe**：反向开始前，第 0 段攒了全部 $`M`$ 个 micro-batch 的激活，峰值显存 $`M\cdot A$`。
- **1F1B**：一段在任意时刻"在途"（已前向、未反向）的 micro-batch 数不超过 $`P-i`$ 个（第 $`i`$ 段），全线峰值出现在第 0 段，约为 $`P\cdot A$`。

用第 3 节的数算一下：$`P=8`$，$`M=32`$，假设 $`A=2\,\text{GB}`$（ hidden 4096、序列 2048、每段 10 层、micro-batch 为 2 时的量级估计，具体值随模型和配置变化）：

| 调度 | 峰值激活显存（第 0 段） |
|---|---|
| GPipe | $`32\times 2\,\text{GB}=64\,\text{GB}`$ |
| 1F1B | $`8\times 2\,\text{GB}=16\,\text{GB}`$ |

省了 48 GB——这就是 1F1B 成为工业标准的原因。再叠加第 16 篇的梯度检查点（只存段边界、反向时重算），激活显存还能再压一个量级，代价是约 30% 的额外前向计算。两者组合是今天大模型训练的默认配置。

别忘了同一张卡上还有权重的账：流水线把权重也切开了，每段只存 $`1/P`$ 的参数。按第 32 篇的记账（混合精度 + Adam，每参数 16 字节）：一个 70B 参数的模型，单卡要存 $`70\times 16=1120\,\text{GB}`$ 的模型状态，远远超过任何单卡；切成 $`P=8`$ 段后，每段约 $`140\,\text{GB}`$——仍然超过一张 80 GB 的卡，还要再叠加 ZeRO 切优化器状态、或张量并行继续切。这就是第 31 篇说的 3D 并行：三种切分不是"三选一"，而是叠加使用，每种解决一种"不够"。

> 适用边界：$`P\cdot A`$ 是"每段耗时相等、严格按 1F1B 执行"的上界估计；实际框架里 warmup 长度、通信重叠方式会让峰值略有出入，但 $`M\to P`$ 这个量级关系是稳的。

## 6. 交错流水线：再切 $`V$` 段，气泡再除以 $`V`$

GPipe 和 1F1B 都还有 $`\frac{P-1}{M+P-1}`$ 的气泡。能不能再压？Megatron-LM 的**交错流水线（interleaved pipeline）**给了一个思路：把每张卡上的模型再切成 $`V`$ 个小段（称为 chunk），每张卡轮流执行属于自己的 $`V$` 个 chunk。

直觉是：气泡的大小由"一个 micro-batch 穿过一段的时间"决定。把一段切成 $`V`$ 个 chunk 后，单个 chunk 的耗时变成原来的 $`1/V`$，填满和排空的绝对时间跟着缩水，而总计算量不变。在每 chunk 耗时相等的理想模型下，气泡占比变为：

```math
\text{气泡占比}\approx\frac{P-1}{M\cdot V+P-1}
```

用第 3 节的数（$`P=8`$，$`M=32`$，$`V=4`$）：气泡从 $`7/39\approx 18\%`$ 降到 $`7/135\approx 5.2\%`$。只取 $`V=2`$ 时也有明显收益：$`7/(64+7)\approx 9.9\%`$，气泡几乎减半。

天下没有免费的午餐，代价有三条：

1. **通信次数变为 $`V`$ 倍**：chunk 之间也要传激活，边界从 $`P-1`$ 个变成 $`V\cdot(P-1)$` 个；
2. **激活显存上升**：同一时刻在途的 micro-batch 更多，第 5 节里"不超过 $`P`$ 份"的上界会被突破，具体倍数取决于实现细节；
3. **调度复杂度上升**：warmup 和稳态的编排更精细，出错更难调试。

所以 $`V$` 取多大（实践中常取 2–4）是**需实验验证**的工程选择，不是公式推导的结论。更激进的还有零气泡（Zero Bubble）调度，用额外重排换时间，本文不展开。

## 7. 流水线并行 vs 张量并行：通信量与适用场景

第 31 篇留了一个问题：三种并行怎么分工？答案藏在通信量里。

**流水线并行**的通信只发生在 $`P-1`$ 个段边界上：前向传激活、反向传梯度，每次传一个 micro-batch 在一个边界上的量——$`\text{micro-batch}\times\text{序列长度}\times\text{hidden}`$ 个数，与模型层数无关。算一笔：micro-batch 为 1、序列 4096、hidden 8192、fp16 时，一次边界传输约 $`4096\times 8192\times 2\,\text{B}\approx 64\,\text{MB}`$；$`P=8`$ 时一个 global batch 的全部边界通信约 $`7\times 2\times 64\,\text{MB}\approx 0.9\,\text{GB}`$。

**张量并行**的通信发生在**每一层**：每层的前向和反向各要做两次 all-reduce（注意力后一次、MLP 后一次），80 层的模型就是 320 次集合通信。单次量级与流水线边界相近，但次数是层数级别。结论：张量并行的通信量比流水线并行高出一个"层数"量级。

把次数算得更细一点：一个 micro-batch 走过 80 层，就是 $`80\times 4=320`$ 次集合通信，每次传输 $`b\cdot s\cdot h`$ 个数（$`b`$ 为 micro-batch 大小，$`s`$ 为序列长度，$`h`$ 为 hidden 维度）。相比之下，同样一个 micro-batch 走过 $`P=8`$ 的流水线，只在 7 个边界上传输，前向加反向一共 $`7\times 2=14`$ 次点对点通信。320 次对 14 次——这就是"张量并行放节点内、流水线并行跨节点"的定量依据。注意这个比较用的是**次数**，不是总字节数：all-reduce 的单次数据量会随张量并行度分摊，而流水线边界传输不分摊；但在跨节点带宽受限时，次数往往比字节数更能决定实际耗时。

最后把通信时间加回第 2 节的公式。设一次边界传输耗时 $`c`$（前向传激活一次、反向传梯度一次），若通信完全不能与计算重叠，每段每 micro-batch 的有效耗时从 $`t`$ 变成 $`t+2c$`，总时间变为 $`(M+P-1)\cdot(t+2c)`$。用第 3 节的数：$`t=100\,\text{ms}`$，$`c=10\,\text{ms}`$，总时间从 $`3.9\,\text{s}`$ 变成 $`4.7\,\text{s}`$，气泡占比也随之上升。现代框架用双缓冲和异步传输把通信与计算重叠，实际增加量小于 $`2c`$——能重叠多少，取决于网卡带宽和计算密度的相对大小，是**需实验验证**的实测值，不是公式能算出来的。

这就决定了 3D 并行的标准分工：

| 并行方式 | 通信特点 | 适合放在 |
|---|---|---|
| 张量并行 | 每层 all-reduce，频繁 | 同一节点内（NVLink 高速互联） |
| 流水线并行 | 只在段边界点对点传激活/梯度 | 跨节点（慢速互联也能接受） |
| 数据并行 | 每步一次 all-reduce 传梯度 | 跨节点、跨机架 |

举个具体的拼法：64 张卡训练一个大模型，可以排成数据并行 2 × 张量并行 4 × 流水线并行 8（$`2\times 4\times 8=64`$）。同一节点内的 4 张卡做张量并行（共享一层的计算），8 个节点排成流水线（每节点拿一段层），2 组这样的流水线再做数据并行（各吃一半数据）。三者的乘积等于总卡数，每种并行各解决一种瓶颈：张量并行分摊单层计算、流水线并行分摊层数、数据并行分摊数据。排布时有个经验顺序：张量并行度最小（通信最频繁，放最快的互联上），流水线其次，数据并行最大（通信最稀疏）。具体数字是**需实验验证**的工程选择，但"TP 在节点内、PP 跨节点、DP 跨一切"这个分工直觉是稳的。

还有两条容易被忽略的性质：

- **流水线并行不改变数学**。与数据并行（改变有效 batch 大小、进而改变优化动态）不同，流水线并行只是执行顺序的重排，前向/反向的数学结果与单卡完全一致（在确定性计算的假设下）。所以它不需要像第 30 篇那样重新调学习率。
- **段不均衡是隐形气泡**。第 2 节假设各段耗时相等；真实切分里，embedding 层和 lm_head 往往让首尾两段更重，某一层特别大也会让某一段拖后腿。最慢的段决定整条线的速度——切分要按计算量均衡，而不是按层数平均分。具体怎么切，是**需实验验证**的调优工作。

## 8. 常见误区

- **"段数越多越快"**——错。加速比上限是 $`P`$，但气泡占比 $`\frac{P-1}{M+P-1}`$ 随 $`P`$ 增大而增大；$`P`$ 翻倍、$`M`$ 不变时，气泡占比上升、通信边界也变多。卡多不等于快。
- **"1F1B 比 GPipe 快"**——错。理想模型下两者总时间完全相同；1F1B 省的是激活显存，省出的显存换更大的 $`M`$，才能间接压气泡。把显存收益说成时间收益，是偷换概念。
- **"流水线并行改变了训练数学"**——错。流水线并行是纯执行顺序重排；改变有效 batch、进而改变优化动态的是数据并行和梯度累积。
- **"micro-batch 越大越好"**——错。global batch 固定时，micro-batch 越大 → $`M`$ 越小 → 气泡占比越大；同时 kernel 效率可能提升。两个方向相反，净效果要实测。
- **"气泡只在训练刚开始时存在"**——错。每个 global batch 都要经历一次填满和排空，气泡是按 optimizer step 重复出现的；训练跑一万步，就要付一万次气泡。
- **"流水线并行只适用于训练"**——错。推理时同样可以把模型切段排成流水线：多个请求以 micro-batch 的形式流过各段，首 token 延迟由填满时间决定，吞吐由最慢一段决定。推理的流水线没有反向，调度更简单，但"填满—排空"的气泡逻辑完全相同。
- **"气泡是通信造成的"**——不完全对。公式里的气泡来自"依赖链 + 填满/排空"，即使通信时间为零它也存在；通信延迟会让它更大，但不是它的来源。

## 9. 自测题

1. $`P=4`$，$`M=16`$，每 micro-batch 每段耗时 $`t=50\,\text{ms}`$，流水线总时间是多少？气泡占比是多少？
   - 答：总时间 $`(16+4-1)\times 50\,\text{ms}=950\,\text{ms}`$；气泡占比 $`3/19\approx 15.8\%`$。
2. 为什么 $`M=P`$ 时气泡占比接近一半？
   - 答：$`\frac{P-1}{M+P-1}=\frac{P-1}{2P-1}`$，$`P`$ 较大时趋近于 $`1/2`$。直观上：填满和排空各占约一半时间，只有中间一小段是全满的。
3. GPipe 下第 0 段峰值要存多少份 micro-batch 的激活？1F1B 呢？
   - 答：GPipe 要存 $`M`$ 份；1F1B 不超过 $`P`$ 份（第 0 段最多约 $`P`$ 份）。
4. global batch 固定，把 micro-batch 翻倍（$`M`$ 减半），气泡占比怎么变？为什么？
   - 答：变大。因为气泡占比 $`\frac{P-1}{M+P-1}`$ 的分母变小了。但 micro-batch 变大可能提升 kernel 效率，净效果需实验验证。

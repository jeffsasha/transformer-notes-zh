# 43｜前缀缓存：相同的系统提示词，为什么只算一次就够了？

> **阅读目标**：理解前缀缓存（Prefix Caching）为什么能跳过重复的 prefill 计算；能从因果注意力出发推导"块的 KV 只能整条前缀一起复用"、算出 Llama-3.1-8B 下一个 4096 token 的系统提示词占多少显存、省多少 prefill 算力，并说清 vLLM 的块级哈希链与 SGLang 的 RadixAttention 基数树在匹配粒度和淘汰策略上的区别。
>
> **前置知识**：第 02 篇的缩放点积注意力（Q、K、V 投影与打分）；第 05 篇的 RoPE（K 的旋转依赖绝对位置）；第 08 篇的 KV Cache（推理时每个 token 的 K、V 常驻显存，缓存大小随 batch 与序列长度线性增长）；第 37 篇的 PagedAttention（KV 缓存按 16 token 的块分页分配）；第 38 篇的连续批处理（请求到达即插队、GPU 不能闲着）。

## 1. 直觉：同一个系统提示词，为什么要算一千遍？

第 08 篇算过一笔账：生成时每个 token 的 K、V 都要常驻显存；第 37 篇解决的是这些缓存"碎成一地"的问题。但还有一笔更隐蔽的浪费，藏在**请求之间**。

想象一个在线客服的推理服务。每个请求都以同一段 4096 token 的系统提示词开头——角色设定、工具定义、回答规范——然后才接上用户真正的问题。1000 个并发请求，就是 1000 次对同一段文本的 prefill：同样的 token、同样的权重、算出 1000 份**数值上完全相同**的 K、V，再把其中 999 份扔掉。

这不是个小数目。第 5 节会具体算：8B 模型上，4096 token 的 prefill 约 65 TFLOPs，在 H100 上约 0.16 秒；1000 个请求就是 160 秒的 GPU 时间，全花在重复计算上。更糟的是多轮对话：每一轮的新请求都把前面所有轮次的对话历史当作前缀重新算一遍，第 10 轮要算的 token 数是第 1 轮的 10 倍。

前缀缓存的回答只有一句话：**算过的 K、V 留着，下一个请求如果以同样的 token 开头，直接拿来用，跳过 prefill**。它不改变任何数值结果——复用的 K、V 和重新算出来的一模一样，输出分布严格不变。它省的只是重复劳动。

但"直接拿来用"有一个前提，需要严格推导：一个 token 的 K、V 到底由什么决定？如果答案是"只由它自己"，那按 token 内容哈希、随取随用就行；如果答案是"由它前面所有 token 决定"，那复用的条件就苛刻得多——必须整条前缀都相同。这个区别决定了整个前缀缓存的工程形态。

> 结论性质：下面"前缀缓存输出严格不变"是**严格推导**（第 2 节）；"能省多少时间、命中率多高"是**严格推导的算术**加上**经验性**的工作负载假设（第 5、6 节）；两种引擎的具体默认行为（默认块大小、默认开关）是**工程事实**，以官方文档为准，版本升级可能变化。

## 2. 为什么不能按 token 内容哈希：K 的值由整条前缀决定

先看一个 token 的 K、V 是怎么来的。标准 Transformer 里，第 $t$ 个 token 的 K 是：

```math
k_t = W_K h_t
```

其中 $h_t$ 是该 token 在某一层的 hidden state。关键在 $h_t$ 本身：经过若干层注意力之后，$h_t$ 已经"看过"了 $0$ 到 $t$ 的所有 token——

```math
h_t^{(l)} = f\big(h_0^{(l-1)}, h_1^{(l-1)}, \dots, h_t^{(l-1)}\big)
```

因果注意力保证 $h_t$ 只依赖位置 $\le t$ 的 token，但**确实依赖全部这些 token**，而不只是它自己。于是：

- 两个请求里第 $t$ 个 token 的字面内容相同，$k_t$ 也未必相同——只要它前面的任何一个 token 不同，$h_t$ 就不同，$k_t$ 就不同。
- 只有当 $0$ 到 $t$ 的**全部 token 都相同**时，$k_t$ 才保证相同。

这就是前缀缓存的第一条铁律：**复用的单位是前缀，不是 token**。一个块（block）的 K、V 只有在其"前面所有内容都相同"的前提下才能复用。单独按 token 内容哈希去匹配，是错的——同一个词"银行"出现在"河边的银行"和"中央银行"之后，K 完全不同。

这个铁律直接决定了 vLLM 的设计：块的哈希必须"链式"计算。把序列按固定块大小（默认 16 token）切分，第 $i$ 个块的哈希定义为：

```math
H_0 = \mathrm{Hash}(\mathrm{tokens}_0), \quad H_i = \mathrm{Hash}(H_{i-1}, \mathrm{tokens}_i) \quad (i \ge 1)
```

$H_i$ 里混入了 $H_{i-1}$，而 $H_{i-1}$ 又混入了更早的所有块——于是 $H_i$ 实际上是"从头到第 $i$ 块全部内容"的指纹。两个请求的第 $i$ 块哈希相等，当且仅当它们从头到第 $i$ 块的 token 序列完全相同。这正是铁律要求的条件，一字不多、一字不少。

匹配过程也因此是"顺序扫描、遇 miss 即停"：新请求到来时，引擎从第 0 块开始逐块查哈希表，一旦第 $k$ 块 miss，立刻停止——后面的块即使内容撞上了也不能用，因为它们的前缀已经不同了。命中 $k$ 个块，就跳过 $k \times 16$ 个 token 的 prefill，从第 $k$ 块之后开始算。

还有一个细节值得注意：RoPE（第 05 篇）给 K 的旋转依赖**绝对位置**。缓存里的 K 是在位置 $0, 1, \dots$ 上算出来的；新请求复用这段前缀时，前缀同样占据位置 $0, 1, \dots$，旋转角对得上，复用才成立。如果某个系统允许把一段缓存"平移"到别的起始位置再用，RoPE 的角度就全错了——所以前缀缓存只复用"从位置 0 开始的相同前缀"，不做位置平移。这是 RoPE 与缓存机制之间一个真实的耦合点。

## 3. vLLM 的做法：块级自动前缀缓存（APC）

vLLM 在 2024 年引入自动前缀缓存（Automatic Prefix Caching，APC），建立在第 37 篇的 PagedAttention 之上。PagedAttention 已经把 KV 缓存切成 16 token 的块、用一张块表管理每条请求的物理块；APC 只是多维护了一张全局哈希表：

```math
\mathrm{HashMap}: H_i \longrightarrow \text{物理块 ID}
```

工作流程分三步：

1. **查找**：新请求按 16 token 切块，逐块算链式哈希、查表。命中 $k$ 个块，就把这 $k$ 个物理块直接挂到新请求的块表上，跳过这部分 prefill。
2. **计算剩余部分**：从第 $k$ 块之后开始正常 prefill。新算出来的块也顺手算哈希、登记进表，供后来的请求复用。
3. **淘汰**：缓存占的是 GPU 显存，而显存首先要服务正在运行的请求。APC 用**引用计数 + LRU**管理：正在被某个运行中请求使用的块引用计数 $> 0$，不能淘汰；空闲块按最近最少使用（LRU）淘汰。请求结束后，它的块不会立刻释放——引用计数归零后留在表里，等着被复用，实在缺显存时才按 LRU 淘汰。

这个设计的收益与代价都写在粒度里。块大小 16 意味着：

- 一段 100 token 的共享前缀，只能复用 $\lfloor 100/16 \rfloor = 6$ 个块，即 96 个 token，剩下 4 个 token 所在的"半块"必须重算。
- 两个请求共享 20 token、但在第 17 个 token 处分叉：只有第 0 块（token 0–15）哈希相同，第 1 块因包含不同的第 17 个 token 而 miss，于是只复用 16 个 token，剩下 4 个共享 token 也要重算。

块是 16 的倍数这个"取整损耗"，是块级缓存为简单管理付出的固定税。系统提示词通常是几百到几千 token，损耗不到一个块，可以忽略；但短前缀（比如只有 20 token 的 few-shot 示例）复用率会被这个取整明显拉低。

APC 还有一个调度层面的配合：第 38 篇的连续批处理让请求随到随跑，而 APC 让"刚跑完的请求留下的块"立刻能被下一个请求用上。多轮对话是最典型的受益者：每一轮的新请求，前缀就是上一轮的全部历史，命中率随轮次自然走高。

## 4. SGLang 的做法：RadixAttention 基数树

vLLM 的哈希表是"扁平"的：它只知道"某段前缀存在"，不知道不同前缀之间"在哪里分叉"。SGLang（Zheng 等，arXiv:2401.05727，2024 年）的 RadixAttention 把缓存组织成一棵**基数树（radix tree / 压缩前缀树）**，树本身就是前缀之间的分叉结构：

- 根节点是空前缀；每条边 carries 一段 token 序列；每个节点指向一段物理 KV 缓存。
- 从根走到某个节点的路径，就是一段完整的前缀；两条路径在某个节点分叉，说明两个请求共享前缀、到此为止开始不同。

新请求到来时，引擎沿着 token 序列在树上走，走到走不下去为止——走到的最深节点就是**最长可复用前缀**。匹配的粒度不再是 16 的整块，而是 token 级：共享 100 token 就复用 100 token，不用凑整到 96。

树是动态生长的。当新请求与已有节点**部分重合**时，节点会**分裂**：比如已有节点存着 token 序列 $[a, b, c, d]$，新请求的前缀是 $[a, b, e]$，引擎就把节点拆成 $[a, b]$ 和 $[c, d]$ 两段，$[a, b]$ 成为公共父节点，再挂上新分支 $[e]$。分裂后，原来那段缓存的引用关系保持不变，只是树形更贴合真实的分叉。

淘汰同样按 LRU，但单位是**叶子节点**：引用计数为 0 的叶子按最近最少使用淘汰；一个节点被淘汰后如果父节点变成叶子且引用计数为 0，也可以继续向上回收。多轮对话、Agent 的多分支探索（同一段历史、多个不同续写）、带工具定义的长系统提示词，都是这棵树最擅长的形状——它们天然就是"一棵前缀不断分叉的树"。

两种实现的对比可以总结成一张表：

|  | vLLM APC | SGLang RadixAttention |
|---|---|---|
| 组织结构 | 扁平哈希表：哈希 → 物理块 | 基数树：路径即前缀 |
| 匹配粒度 | 块级（默认 16 token） | token 级 |
| 命中条件 | 链式哈希逐块相等，遇 miss 即停 | 沿树走到最深的可达节点 |
| 分叉处理 | 分叉后的块无法共享结构信息 | 节点分裂，共享部分只存一次 |
| 淘汰 | 引用计数 + LRU（按块） | 引用计数 + LRU（按叶子节点） |
| 开关 | `--enable-prefix-caching` 显式开启（V1 之后逐步默认开启） | 默认开启 |

这张表里的"开关"一行是工程事实、随版本变化，读的时候以官方文档为准。结构上的区别才是稳定的结论：**扁平表回答"这段前缀有没有"，树回答"最长共享前缀到哪里、以及各条前缀之间怎么分叉"**。Agent 场景里多分支共享同一段历史，树省下的不只是几个 token 的取整损耗，还有重复存储的整段分支。

还有一层容易被忽略的扩展：**多实例部署时的缓存感知路由**。前缀缓存只存在于单台机器的显存里——请求被负载均衡打到哪台机器，哪台机器的缓存才可能命中。如果十台机器轮询接请求，同一段系统提示词的缓存会在十台机器上各存一份、各自冷热不均。SGLang 的做法是让路由层也"认识"前缀：按请求前缀的哈希把请求定向到最可能已经缓存了这段前缀的实例上，让命中率从"单机内"扩展到"集群内"。这是**工程实现**层面的优化，不改变第 2 节的数学结论，但它说明了一点：前缀缓存的收益天花板不只取决于缓存结构，还取决于请求是怎么被分发的。

## 5. 数值示例：一个系统提示词到底值多少钱

拿一个具体的模型算账：Llama-3.1-8B（32 层、8 个 KV 头——GQA，第 09 篇——头维 128，fp16）。

**每个 token 的 KV 缓存多大？**

```math
\text{每 token KV 字节数} = 2 \times 32 \text{ 层} \times 8 \text{ 头} \times 128 \text{ 维} \times 2 \text{ 字节} = 131{,}072 \text{ 字节} = 128 \text{ KiB}
```

**一个 4096 token 的系统提示词：**

- 缓存大小：$4096 \times 128 \text{ KiB} = 512 \text{ MiB}$——只存一份。
- prefill 算力（主导项是 $2PT$，$P = 8\times10^9$ 参数，$T = 4096$ token；注意力二次项约占 7%，先忽略）：

```math
\text{FLOPs} \approx 2 \times 8\times10^9 \times 4096 \approx 6.6\times10^{13} = 65 \text{ TFLOPs}
```

H100 的 fp16 dense 算力约 990 TFLOPS，实际利用率按 40% 算约 400 TFLOPS，单次 prefill 约 $65/400 \approx 0.16$ 秒。

**1000 个请求共享这段系统提示词：**

|  | 不用前缀缓存 | 用前缀缓存 |
|---|---|---|
| prefill 总算力 | $1000 \times 65 = 65{,}000$ TFLOPs（约 160 秒 GPU 时间） | $65$ TFLOPs（约 0.16 秒，只算一次） |
| KV 缓存总占用 | $1000 \times 512 \text{ MiB} = 512 \text{ GiB}$ | $512 \text{ MiB}$（一份共享） |
| 新请求的 TTFT | 约 0.16 秒起步 | 接近 0（只算用户问题那几十个 token） |

注意第二行：没有前缀缓存时，1000 个请求**同时在线**才会各占 512 MiB；顺序处理时缓存会复写，显存账没这么夸张。但算力账是实的——每个请求都要重新算一遍 65 TFLOPs，省不掉。TTFT（首 token 延迟）也一样：系统提示词越长，用户等第一个 token 的时间越久；命中缓存后，TTFT 只剩下用户问题本身的 prefill，往往从几百毫秒降到几十毫秒。

**多轮对话的账更直观。** 设每轮新增 300 token（用户问题 + 模型回复），10 轮后对话共 3000 token。不用缓存时，第 $k$ 轮要 prefill $300k$ 个 token，10 轮累计：

```math
300 \times (1 + 2 + \cdots + 10) = 300 \times 55 = 16{,}500 \text{ token}
```

用前缀缓存时，每轮只算新增的 300 token，10 轮累计 $3000$ token。**省了 5.5 倍**，而且轮次越多、倍数越大——这是"前缀"随对话线性增长、而"重复计算"随轮次平方增长的必然结果（$\sum_{k=1}^{n} k = n(n+1)/2$）。

衡量这一切的指标很简单：

```math
\text{缓存命中率} = \frac{\text{命中 token 数}}{\text{命中 token 数} + \text{未命中 token 数}}
```

vLLM 把它记为 `num_prefix_cache_hit_tokens`，SGLang 记为 `sglang:cache_hit_rate`。系统提示词、工具定义高度重合的 Agent 场景里，这个数字常常超过 90%——但这是**经验性**的结论，取决于工作负载；提示词各不相同的场景里，它接近 0，前缀缓存纯粹是摆设。

**命中率要多高才值得开？** 这笔账比想象中宽松。一次缓存查找只是一次哈希表查询，成本是 $O(1)$、可以忽略；一次命中省下的则是实打实的 $2P$ FLOPs/token 的 prefill 计算。所以在**算力账**上，只要命中一次就是净赚，没有盈亏平衡点的问题。真正的成本在另一边：缓存占显存。命中率为 0 时，缓存表里躺着永远没人复用的块，白白挤占并发空间；命中率稍高一点，这些显存就换来了成倍的算力节省。工程上的经验法则是：**看命中率，更要看"缓存占用显存 / 总显存"**——命中率 5% 但只占 1% 显存，照样值得开；命中率 50% 却占了 40% 显存，就要权衡是不是把并发数压下来了。这个权衡没有通用公式，是**需实验验证**的部署参数。

## 6. 边界与误区：前缀缓存省什么、不省什么

**第一，省的是 prefill，不省 decode。** 前缀缓存跳过的是"算 K、V"这一步。生成阶段每步仍要读全部历史 K、V、做一次注意力（第 08 篇），decode 的成本一分不少。TTFT 会大幅下降，但每个 token 的生成间隔（TPOT）基本不变。把前缀缓存当成"推理全面提速"，是错的。

**第二，收益取决于前缀重合度，不是模型大小。** 同一个模型、同一套系统提示词服务 1000 个用户，命中率 90% 以上；每人提示词都不同，命中率就是 0。部署前先看流量特征：系统提示词占比越高、多轮对话越长，收益越大。反过来，单次问答、提示词全随机的服务，开着缓存也几乎没有收益，只是多占了显存。

**第三，缓存占的显存是"借来的"。** 被缓存的块占着 GPU 显存，而这些显存本可以用来跑更多并发请求。命中率低时，缓存就是纯开销——占着茅坑不拉屎。好的实现（引用计数 + LRU）保证活跃请求永远优先，缓存只用"闲置"显存；但闲置显存本身也是有限的，缓存池大小需要按工作负载调参。

**第四，和滑动窗口注意力（第 41 篇）有个有趣的交互。** 如果模型是**纯**滑动窗口——所有层都只看最近 $w$ 个 token——那么超出窗口的前缀对后续生成**没有任何影响**（注意力读不到它，FFN 是逐位置的、不跨 token 混信息）。这种情况下，缓存一段超长前缀的收益只剩窗口内那一段；更进一步说，窗口外的前缀连算都不用算。但多数模型会混用全局层（比如每隔几层放一个全局注意力层），这时窗口外的前缀又通过全局层产生了影响，结论要按具体架构重新算。

**第五，多租户场景下有个真实的安全注脚。** 缓存命中与否会反映在延迟上：一个精心构造的请求如果命中了缓存（TTFT 异常地短），就泄露了"这段前缀曾经被别人提交过"这一比特信息。共享推理服务里，系统提示词往往是公开的、问题不大；但如果用户把隐私内容放进"共享前缀"的位置，时序侧信道理论上可以探测它。这是**需实验验证、取决于具体部署**的风险，不是前缀缓存本身的数学缺陷——缓解办法包括按租户隔离缓存、或对敏感前缀禁用跨请求复用。

## 7. 常见误区

**误区 1："只要 token 相同，K、V 就能复用。"**

错。第 2 节推导过：$k_t$ 依赖 $0$ 到 $t$ 的全部 token。两个请求在第 100 个 token 处用了同一个词，但前 99 个 token 有一个不同，第 100 个 token 的 K、V 就不同。复用的单位是前缀，不是 token；链式哈希 $H_i = \mathrm{Hash}(H_{i-1}, \mathrm{tokens}_i)$ 正是为了把这个条件编码进匹配规则。

**误区 2："前缀缓存让推理变快，所以吞吐量也翻倍。"**

只对了一半。它降低 TTFT、减少 prefill 占用的 GPU 时间，从而**间接**抬高系统吞吐——省下来的算力可以服务更多请求。但 decode 阶段（第 08 篇：显存带宽 bound）不受影响；如果系统瓶颈本来就在 decode，前缀缓存几乎不改变吞吐上限。瓶颈在哪，收益就在哪。

**误区 3："命中率 100% 就是最好，缓存越大越好。"**

错。命中率 100% 意味着所有请求共享同一前缀——这时缓存确实零浪费。但缓存池无限制地变大并不会继续提高命中率，反而挤占活跃请求的显存，逼得系统降低并发、甚至触发更频繁的淘汰。最优缓存大小是工作负载的函数，不是越大越好。

**误区 4："vLLM 和 SGLang 的前缀缓存是一回事，只是名字不同。"**

机制目标相同，实现结构不同。vLLM 是扁平哈希表、块级匹配；SGLang 是基数树、token 级匹配、节点分裂。短前缀、分支多的 Agent 流量下，树的取整损耗更小、分叉共享更彻底；简单场景下两者收益接近。选型时看流量形状，不看名字。

**误区 5："前缀缓存改变了模型输出。"**

错。复用的 K、V 与重新算出的 K、V 在数学上完全相同（浮点实现细节除外：同一段前缀在不同 batch 形状下算出的浮点结果可能有最后一位的差异，但这属于数值噪声量级，不影响分布）。前缀缓存是纯工程优化，不改变模型行为——这也是它能默认开启的底气。

## 8. 自测题

**Q1.** 两个请求的前 200 个 token 完全相同，第 201 个 token 不同。vLLM（块大小 16）能复用多少个 token 的 KV？为什么？

<details>
<summary>答案</summary>

复用 $\lfloor 200/16 \rfloor = 12$ 个块，即 192 个 token。第 12 块（token 192–207）包含不同的第 201 个 token，链式哈希 $H_{12}$ 不同，匹配在第 12 块 miss 即停，后面的块即使内容相同也不能复用。8 个共享 token（193–200）也因为"半块"而被迫重算——这就是块级粒度的取整损耗。

</details>

**Q2.** 用第 5 节的数字：Llama-3.1-8B、fp16、系统提示词 8192 token。只存这一份前缀缓存要多少显存？100 个请求共享它，不用缓存时 prefill 总算力是多少（只算 $2PT$ 主导项）？

<details>
<summary>答案</summary>

每 token 128 KiB，8192 token 占 $8192 \times 128 \text{ KiB} = 1 \text{ GiB}$。单次 prefill FLOPs $\approx 2 \times 8\times10^9 \times 8192 \approx 1.3\times10^{14}$，100 个请求共 $1.3\times10^{16}$ FLOPs；前缀缓存把它压到一次，即 $1.3\times10^{14}$ FLOPs，省 99%。

</details>

**Q3.** 为什么 RoPE 的存在意味着前缀缓存只能复用"从位置 0 开始"的相同前缀，而不能把一段缓存平移到别的起始位置？

<details>
<summary>答案</summary>

RoPE 给第 $m$ 个位置的 K 乘上旋转角 $m\theta$。缓存里的 K 是在位置 $0, 1, \dots$ 上算出来的、带着这些位置的旋转角；如果把它平移到从位置 $s$ 开始用，正确角度应该是 $(s + m)\theta$，缓存里的 $m\theta$ 全错了，打分 $q_m^T k_n$ 依赖的相对位移也不再是 $m - n$。所以只有起始位置相同的复用才是数学上成立的。

</details>

**Q4.** 一个多轮对话服务：每轮新增 200 token，共 20 轮。不用前缀缓存时，累计 prefill 多少 token？用了之后是多少？倍数是多少？

<details>
<summary>答案</summary>

不用缓存：第 $k$ 轮 prefill $200k$ token，累计 $200 \times (1+\cdots+20) = 200 \times 210 = 42{,}000$ token。用缓存：每轮只算新增的 200 token，累计 $200 \times 20 = 4{,}000$ token。省了 $42{,}000 / 4{,}000 = 10.5$ 倍。轮次越多倍数越大，符合 $\sum k = n(n+1)/2$ 的平方增长规律。

</details>
